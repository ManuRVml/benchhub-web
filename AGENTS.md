# AGENTS.md — eco-comparator-web

Rules for every agent (and human) working in this repo. `CLAUDE.md` only points here.

This repo is the React SPA of Eco-Comparador (BencHUD). It is presentation only: all data comes from
`eco-comparator-bff` through a versioned HTTP contract. Code, identifiers, commits and comments are in English; visible
UI copy is es-CO and always goes through i18n.

Paths marked `(planned)` do not exist yet; the task that creates them is named next to them. `node
tools/check-agents-md.mjs` checks that every other path in backticks exists.

## Rules

### Common rules

1. Read `docs/progress/STATUS.md`, this file and the relevant ADRs in `docs/architecture/adr/` (index:
   `docs/architecture/adr/README.md`) before you touch code. For screen work, also read the screen's file in
   `docs/design/screen-inventory/` and its contracts in `docs/design/view-data-contracts/`.
2. Run `pnpm verify` (`pnpm lint && pnpm typecheck && pnpm test`) before you finish; never deliver with lint, types or
   tests in red. The hooks enforce part of this: `.husky/pre-commit` runs lint-staged (`eslint --max-warnings 0` and
   `prettier --check` on code files; `docs/` and `*.md` are Prettier-ignored) and `.husky/commit-msg` runs commitlint.
3. Respect the layer boundaries. Feature-Sliced Design is enforced by `eslint.config.js` with the rules in
   `tools/architecture/fsd-rules.js` (`pnpm lint`, `pnpm check:architecture`, `pnpm check:architecture:selftest`). If the
   architecture lint fails, fix the design, not the rule.
4. Never use `any`, `@ts-ignore` or `eslint-disable` without a justification and a link to an ADR or issue, on the same
   line: `// eslint-disable-next-line <rule> -- <reason> (ADR-0003)`.
5. All new code ships with tests: Vitest unit and component tests next to the code (`*.test.ts` / `*.test.tsx`),
   Playwright specs in `e2e/`, and checker scripts with a mutation that proves they fail.
6. Never import code from the other repo (`eco-comparator-bff`): no relative paths, workspace links or copied sources.
   The only boundary is the published contract, vendored and pinned in `contract.lock.json` (ADR
   `docs/architecture/adr/0004-contract-consumption.md`).
7. Small commits with Conventional Commits (commitlint: header and body lines ≤ 100 characters). Update
   `docs/progress/STATUS.md` at phase boundaries and write an ADR in `docs/architecture/adr/` for every design decision
   (`node tools/check-adrs.mjs` validates them).
8. Use the decision tree "Where does this file go?" and the "Definition of Done" below for every task.

### Web rules

9. A new or derived datum is requested from the BFF by updating the view's contract in
   `docs/design/view-data-contracts/` (one file per view or command; the index `docs/design/view-data-contracts.md` is
   generated by `node tools/build-design-index.mjs`). Never compute business derivations in the front (variations,
   trends, rankings, tiers, compliance, counts, labels); the front only formats raw values by locale and unit.
10. Never edit `src/shared/api/generated/`. Regenerate it with `pnpm contract:generate`
    from the pinned contract version.
11. Components never call `fetch`: data flows through the ports and adapters of `src/shared/api/` and
    TanStack Query hooks. Chart libraries (ECharts) are imported only in `src/shared/ui/charts/`; the
    lint rule in `tools/architecture/fsd-rules.js` blocks them elsewhere (ADR
    `docs/architecture/adr/0003-charts.md`).
12. URL for shareable state (typed search params validated with Zod), TanStack Query for server state, Zustand for UI
    state (ADR `docs/architecture/adr/0005-state-and-url.md`). Route paths are spelled only in
    `src/shared/config/routes.ts` (use `routes.<key>.build()` / `.path`; ADR
    `docs/architecture/adr/0010-routing.md`), also enforced by lint.
13. Every interactive element has a `data-testid` that follows the convention and is registered in the slice's
    `<slice>/test-ids.ts`, or in `src/shared/config/test-ids.ts` for shared UI.
14. Colours, spacing and typography come only from tokens (`docs/design/design-tokens.json` → generated Tailwind
    `@theme`, ADR `docs/architecture/adr/0002-styling.md`); no hex values or arbitrary Tailwind values unless an ADR
    allows them.
15. Visible text always goes through i18n (es-CO). If the prototype and the code differ, the prototype wins unless an
    ADR or a row in `docs/design/conflicts.md` says otherwise (source precedence:
    `docs/architecture/adr/0001-source-precedence.md`).

## Where does this file go?

Layers from top to bottom: `app → pages → widgets → features → entities → shared` (brief §2.5). A layer imports only
layers below it; slices of the same layer never import each other; another slice is imported only through its
public API (`<slice>/index.ts`). Ask the questions in order and stop at the first "yes":

```text
Is it app code (React / TypeScript that ships in the SPA)?
├─ No
│  ├─ Design analysis (inventory, contract, token, overlay, OQ, CF)  → docs/design/
│  ├─ Architecture decision                                          → docs/architecture/adr/NNNN-<topic>.md
│  ├─ Phase status                                                   → docs/progress/STATUS.md
│  ├─ Checker / generator / render script (Node, no deps, exit code) → tools/
│  └─ End-to-end spec or page object                                 → e2e/specs/, e2e/pages/
└─ Yes
   1. App-wide wiring: providers, router, route table, global styles and @theme?  → src/app/
   2. A whole screen (SCR-xx) that only composes widgets and features?           → src/pages/<page>/
   3. A self-contained block of a screen (card, rail, chart section)?            → src/widgets/<widget>/
   4. A user action with its own logic (a command C-xx, form, mutation)?         → src/features/<feature>/
   5. A business entity: model, query hooks, entity UI (company chip, KVI row)?  → src/entities/<entity>/
   6. Domain-agnostic code?                                                      → src/shared/<segment>/
        ui/      design system: primitives, composites, charts/, table/, layout/
        api/     ports, adapters (http, mock), generated/ (never edit), http-client, query-keys
        lib/     formatters (es-CO), utils, cn()
        model/   app-wide UI stores (Zustand), e.g. layout.store
        config/ (routes.ts, test-ids.ts), i18n/
```

Tie-breakers:

- Two pages need the same block: it is a widget, not page code.
- It sends a command (C-xx): it is a feature, even if it is only a button.
- It knows a business term (company, KVI, analysis): it is not `shared`.
- Stories and tests live next to the code they cover (`*.stories.tsx`, `*.test.tsx`).

## Definition of Done

Every task type also needs `pnpm verify` green, a clean `git status`, Conventional Commits, and the evidence (commands
and exit codes) in the delivery message.

| Task type | Must pass | Must exist |
| --- | --- | --- |
| Design doc (`docs/design/`, ADR) | The checker of each touched doc: `node tools/check-view-contracts.mjs`, `node tools/check-command-contracts.mjs`, `node tools/check-open-questions.mjs`, `node tools/check-navigation-map.mjs`, `node tools/check-component-catalog.mjs`, `node tools/check-design-consistency.mjs`, `node tools/check-adrs.mjs`, `node tools/build-design-index.mjs --check`; `pnpm gate:1` for Phase 1 docs | Every quoted copy cites its prototype line or an `[inference]` tag; new decisions are rows in `docs/design/open-questions.md` / `docs/design/conflicts.md` |
| Shared UI component, `src/shared/ui/` | `pnpm verify`, `pnpm check:architecture`, `pnpm build-storybook` | Story per variant and state, test per state, tokens only, `data-testid`, an entry in `docs/design/component-catalog.md` |
| Page | `pnpm verify`, `pnpm test:visual` against the committed baselines (ADR-0011, which supersedes ADR-0007), `pnpm prototype:check` when prototype renders change | Route in `src/shared/config/routes.ts`, loading / empty / error / forbidden / partial states from the screen inventory, i18n keys, `data-testid`s |
| API adapter | `pnpm verify`, `pnpm contract:check` | Port + HTTP adapter + mock adapter, Zod validation of the response, MSW tests per scenario, the view contract in `docs/design/view-data-contracts/` |
| E2E | `pnpm test:e2e` (mock mode with `E2E_PORT`) and `pnpm test:e2e:stack` (with `STACK_URL`) green; machine rule: Playwright `--workers=1` | Page objects in `e2e/pages/`, selectors only by `data-testid`, no fixed sleeps, a mutation proves the check fails |
| Architecture | `pnpm check:architecture` and `pnpm check:architecture:selftest` green; machine rule: `vitest --maxWorkers=1 --no-file-parallelism` | `tools/architecture/fsd-rules.js` enforces layer boundaries, a mutation proves the check fails |

## Working with eco-comparator-bff

- Contract only. The BFF publishes `@eco/bff-contract` (OpenAPI 3.1); this repo pins one version and generates types,
  Zod schemas and the client from it (ADR 0004).
- Need a new field or view: change the contract file in `docs/design/view-data-contracts/` first; the BFF lane copies
  it into its own docs/requirements folder and ships a new contract version.
- Local development runs the BFF `-mock` container image (podman) or the SPA's own mock adapters; never a path to the
  BFF sources.
